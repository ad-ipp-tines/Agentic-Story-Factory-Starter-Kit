# 05 · Pros and cons — honest, and when not to do this

_Tines Stories as Code · docs v1 (2026-09-24) · Matches `DESIGN.md` §8 · Every pro names what makes it true; every con names why and what mitigates it. The "when not to do this" section is the part to read first if you are the one deciding._

## 1. Pros

| # | Pro | What makes it true | Where to check |
|---|---|---|---|
| 1 | **Stories get what code has had for decades** — a diff on every change, an independent review, a merge gate, a rollback point, a nightly drift check. The repo is the truth and the tenant is a deployment target | `GET /api/v1/stories/{id}/export` + `normalize.jq` make exports diff-stable; `POST /api/v1/stories/import` with `versionReplace` re-creates them; `drift.yml` proves prod equals `main` | `stories/**/story.json`, `scripts/`, `.github/workflows/drift.yml` |
| 2 | **Speed with control** — one afternoon from idea to a change request | The build skill carries the procedure and the prompt pack; `lint-on-write.sh` lints every write; `stop-gate.sh` keeps the export fresh; the only manual steps are the ones `/mcp` cannot do, and the skill names them | `.claude/skills/tines-build-story/`, `README.md` "the afternoon" |
| 3 | **Cost is a design property** | The build loop runs on the editor's plan with no Tines credits listed for the Tines Stories MCP server; runtime AI is bounded by schemas, tool caps, token alerts, a daily run cap, a kill switch and file-based budgets; a healthy sweep spends zero credits | `03-cost-controls.md`, `policies/cost-ceilings.yml` |
| 4 | **Security posture is inherited, not invented** | OAuth-only authoring that carries the builder's own permissions and is audit-logged as MCP activity; credentials that never leave Tines and never appear in exports; team-scoped keys that cannot approve; change control with **Require approval for all changes** as the deterministic gate; hooks that enforce rather than request | `04-security-model.md`, `policies/POLICY.md` |
| 5 | **Every control is a file a security reviewer can read and diff** | Permissions, hooks, budgets, the never-touch list, lint rules, CODEOWNERS, workflow gates and the governance contract are all committed text | `.claude/settings.json`, `.claude/hooks/`, `policies/`, `.github/` |
| 6 | **Two independent gates on every production change**, joined by the commit SHA and a story version | A GitHub environment with reviewers **and** a Tines change request approved by a person; no key in CI can approve | `ship.yml`, `promote.yml`, the change-request description template in `scripts/tines cr-open` |
| 7 | **One skills tree serves Cursor and Claude Code**, and the tenant-side Agent Skills live in the same repo with a CRUD API behind them | Cursor reads `.claude/skills/` as a legacy path (VERIFY, item 4); `POST`/`PUT /api/v1/skills` since 2026-09-01; a rename is rewritten by the API in every AI Agent action that references the skill | `.claude/skills/`, `tines-skills/`, `skills.yml` |

## 2. Cons

| # | Con | Why | Mitigation in this repo | Residual |
|---|---|---|---|---|
| 1 | **The Tines Stories MCP server's tool names and count are unpublished** | The docs describe capabilities; the consent screen lists them; no page lists tool names | `guard-mcp.sh` uses an input-based production-ID check that does not depend on names, plus a destructive-name regex; `/tines-connect` records the real names in `VERIFY.md` so the regex becomes a deny list | Skills cannot reference `tines:<tool>` precisely until then (item 1) |
| 2 | **`/mcp` is OAuth only — no headless authoring** | "Authentication uses OAuth only, not API keys"; the Agent SDK does not run an interactive OAuth flow; whether a headless session can reuse an interactive session is undocumented on both sides | CI lints, reviews, imports and opens change requests through the API; every tenant *edit* stays interactive | No scripted bulk edit through `/mcp` (item 20) |
| 3 | **How `/mcp` edits interact with change control and drafts is unpublished** | No public page states it | The repo never authors in prod; the policy is enabled regardless; test events use `?draft=` when needed | A dev-team edit may be live in dev until verified (item 2) |
| 4 | **Story exports are not designed for hand editing** | Links reference agents by index; option keys have no published schema; import matches by name; embedded sub-stories are not imported; MCP connections are dropped; credentials and resources must pre-exist by name in every environment | `story.json` is never typed — always exported; `normalize.jq` preserves agent order; lint keys are set from a real export (item 8); the propose-fix allow-list is three benign kinds | Every lint rule for retry/monitor/schema keys needs one real export before it is exact |
| 5 | **Two teams plus the ops trio cost licences and roughly nine flows** | A flow is charged per autonomous flow (Community 3, Business from 30); Send to Story sub-stories used as tools count on current reading; the AI Agent action is Business/Enterprise only and unavailable in personal teams | `tier: internal` and Workbench-only stories where possible; Custom tools (Groups) consolidation once stable; a `staging` environment is optional, not required | Community tenants cannot run the monitoring agent at all; sub-story counting is VERIFY (item 13) |
| 6 | **No API exists for per-team credit allocation, credit-usage alert thresholds or AI Agent token thresholds** | Admin → AI and the Status tab are UI-only on current evidence | They are set by hand, recorded in `story.meta.yaml` and `cost-ceilings.yml`, and the reviewer refuses a story whose meta lacks the token alert; the agent proposes them as `token_threshold` / `credit_budget` → a Case task or a Record | They can drift from the policy file; the "agentic" part can only propose them |
| 7 | **Cursor picks up `.claude/skills/` as a legacy path and does not run Claude Code hooks** | Different products; Cursor's IDE agent has no PreToolUse/Stop hook model for this repo | Enforcement in Cursor is CI (`lint.yml`, `review.yml`) and Tines change control; `.cursor/rules/story-json.mdc` states it | A Cursor builder gets no local guard against a production id (item 4) |
| 8 | **There is no run-status field** | `GET /api/v1/stories/{id}/runs` returns `duration`, `action_count`, `event_count` — not success/failure | Failure is derived from `not_working_actions_count`, `pending_action_runs_count`, level-4 logs and event counts; the monitoring webhook payload is captured by hand once | A handled failure-path error may also fire "Notify when action fails" — double signals until verified (items 9, 16, 24) |
| 9 | **LLM-edited JSON proposals can break links** | Index-based links; a model editing an export can reorder or drop them | `tines-propose-fix` never reorders agents or changes links; only three fix kinds are applied automatically; lint and review run on the PR | The safer default — an issue with a `/tines-build-story` prompt — adds a human step |
| 10 | **Process overhead for tiny changes** | Branch, PR, two checks, CODEOWNERS, merge, change request, approval — and reviewers must read story JSON; audit noise grows with MCP activity, drift PRs and proposal PRs | `tier: internal` and a lighter path (§4); `diff-story.sh` gives reviewers a semantic diff instead of raw JSON; `cr-view` gives the approver live-vs-draft | Small teams may find the ceremony heavy for low-risk stories |
| 11 | **The Terraform provider is 0.x** | Breaking changes in minors; TEXT credentials only; no skills resource; behaviour on change-controlled stories unverified | Optional, not on the default pipeline; `terraform apply` is denied in the IDE | If you rely on it, you carry the 0.x risk (item 22) |
| 12 | **Mode 2 runs on the editor's provider** | The model is the editor's, so the organisation's editor data policy governs what the model sees, not Tines' foundation guarantees | Exports contain configuration only; the authoring engine cannot see credential values, resource contents or data in flight | Some organisations will need that reviewed before the first build |
| 13 | **The monitor is itself a story that can fail** | Double signals, notification storms, a stale lock, a silent sweep | The router dedupes; the watchdog pages the email DL; the lock has a staleness rule; the ops stories' own recipients are a second channel | It adds failure modes the ops role must own (`02-workflows.md` §4.9) |

## 3. When not to do this

Be honest about fit. This repository is the right shape for a team that ships production automations across environments and answers to a security reviewer. It is the wrong shape in these cases:

| Situation | Why it does not fit | What to do instead |
|---|---|---|
| **A Community Edition tenant** | 3 flows; no AI Agent action; 50 credits/month; Workbench limits — the ops pair cannot run and the flow budget is gone before the first story | Use git for exports and the API for import (that part needs no plan feature); Mode 2 authoring if `/mcp` is available on the tenant (the docs state no plan gating either way — confirm, item 13); skip the ops trio; monitor with the email recipient and the platform's own alerts |
| **A team of one making a small number of changes a month** | Branch → PR → two checks → CODEOWNERS → merge → change request → approval is more ceremony than the risk warrants; nobody independent exists to review | Keep exports in git and change control on; skip `review.yml` and CODEOWNERS; the approver is the same person, which change control still records |
| **No git or GitHub practice on the team** | The system's value is the review, the diff and the gates; without a team that reads PRs, the repo becomes a backup folder | Start with Workbench for Storyboard plus change control; introduce exports-in-git for the two or three stories that matter |
| **The organisation's editor data policy forbids sending story configuration to an external model provider** | Mode 2 runs on the editor's provider; story configuration (action names, formulas, credential *names*) leaves the tenant | Author with Workbench for Storyboard (Tines' foundation guarantees, or a custom provider you control); keep the export/ship/drift pipeline — it needs no model |
| **The tenant's plan lacks change control or the AI Agent action** | The deterministic gate and the monitor both depend on plan entitlements | Confirm the plan mapping (item 13) first; the export/PR/lint path still works, but promotion becomes an API import into a live story, which this repo refuses to automate |
| **Throwaway, exploratory or Workbench-only stories** | A story that will never be published or never leaves one person's team does not need a change request | Build it directly (Workbench or `/mcp`), never export it, or mark it `tier: seed` in the manifest and keep it out of `ship.yml` |
| **You need scripted, unattended bulk authoring today** | `/mcp` is OAuth only; no headless authoring path exists (item 20) | The API/Terraform path for bulk *deployment*; Mode 2 sessions for bulk *editing*, one story at a time, by a person |
| **Sub-second latency, bulk data movement, or a destructive action with no approval path** | Never MCP for these — tool results are context, not a data plane; the 30-second Mode 4 ceiling and the credit meter are the wrong tools | HTTP Request actions, Send to Story, Event Transforms; a request tool with an approval if a human must be in the loop |
| **A tenant with one team and no separate dev team** | Every build would happen next to production; `guard-mcp.sh` cannot tell them apart by team | Create the dev team first (it is the cheapest control in the whole design), or do not connect an editor to the tenant at all |

## 4. A lighter path for low-risk stories

For `tier: internal` stories (no production credentials, no external side effects, a single owning team) the repo allows a lighter loop without changing the controls that matter:

1. Build in the dev team with `/tines-build-story` as usual — the hooks and lint still run.
2. `/tines-export` and commit on a branch; open the PR; `lint.yml` runs; **skip `review.yml`** (path filter on `tier` in meta, or a label) and let CODEOWNERS be the single reviewer.
3. `ship.yml` still opens a change request — change control stays on for every story — but the approver may be the story's own owner.
4. The story still reports to the router (`monitor_failures`, recipients from the manifest); the sweep still baselines it.

What the lighter path never removes: the export in git, lint, change control, monitoring recipients, the never-touch list, and the rule that production is never authored through `/mcp`.
